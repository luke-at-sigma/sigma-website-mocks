3 steps to a live forecast

1
Connect the warehouse

Sigma queries live warehouse tables, so the forecast always reads current actuals without an extract to refresh.

2
Set the drivers

Assumptions live in Input Tables next to the data. Every edit writes back to the warehouse with the user and timestamp.

3
Freeze and compare

Approve a version and it locks. Analysts, managers, and the CFO compare it against actuals in the same workbook.

Questions finance teams ask

Which warehouses can Sigma write a forecast back to?+
Input Table writeback runs on Databricks and Snowflake, and others like BigQuery and Amazon Redshift. Sigma writes to a designated write schema inside your own account, so forecast inputs sit beside the actuals they feed. Your existing roles and row-level security govern every write, and the audit history records who changed what.
How do we stop someone overwriting an approved version?+
Approve the version and lock it. Edits arrive as non-destructive row-level inserts, so the approved rows keep their own state, and audit history holds the full trail. Reviewers compare the locked version against actuals and the current reforecast in the same workbook.
Does Sigma bring its own forecasting model?+
Sigma ships no model of its own. You point Sigma at the LLM provider you already run, or invoke a warehouse-native model. Sigma logs every AI call under your existing warehouse controls. Sigma Agents generate what-if scenarios and track them against real outcomes on Input Table data.
Where do we start building a forecast app?+
Most teams start from an App Template. Revenue forecasting, pipeline forecasting, and demand planning all ship with sample data and a guided source swap that points at your own warehouse tables. From there a builder edits the drivers, periods, and approval steps.
